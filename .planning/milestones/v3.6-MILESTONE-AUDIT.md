## Cross-Phase Integration Findings

The integration check traced the layered proxy/sandbox stack rather than API routes, because
that is where this milestone's real risk sits — phases 109 → 113 → 114 all modified the same
five files in `crates/nono-proxy/src/`.

### NEW-01 — BLOCKER — uncategorised denials on the dominant HTTPS path
*Affects NET-01, SEC-02*

Phase 112 built the structured `NetworkAuditDenialCategory` spine; 113/114 extended it. Three
denial sites were never connected to it and pass `&audit::EventContext::default()`:

- `crates/nono-proxy/src/connect.rs:83-90` — **verified at source.** CONNECT host denied by
  `ProxyFilter`. This is NET-01's `deny_domain` enforcement point for **HTTPS**, i.e. the
  dominant path.
- `crates/nono-proxy/src/external.rs:133-140` and `:197-204` — external-proxy denials.

The identical denial on the other two paths *does* carry the category (`reverse.rs:365-376`,
`server.rs:1146-1156`, both `HostDenied`). So a `deny_domain` block produces a categorised
audit record over plain HTTP and an uncategorised one over HTTPS — any consumer filtering on
`denial_category == HostDenied` silently under-reports enforcement.

`NetworkAuditDenialCategory::ExternalProxyRejected` (`crates/nono/src/undo/types.rs:245`) has
**zero production constructors** — verified independently: its only two workspace references
are nono-py's encoder (`../nono-py/src/proxy.rs:92`) and decoder (`../nono-py/src/undo.rs:613`),
neither of which produces it. The site that should (`external.rs:197`) uses the default context.

Not present in `112-REVIEW.md`, `113-REVIEW.md`, or `114-REVIEW.md` — it is invisible to any
single-phase review because it requires comparing 112's spine against 109's check sites.

### NEW-02 — WARNING (security) — `platform_overrides` can silently drop `capture`/`spiffe` on one OS
*Affects PROF-01 × NET-02 × SEC-02*

**Verified at source.** `crates/nono-cli/src/profile/mod.rs:3683-3687`:

```rust
custom_credentials: {
    let mut merged = base.network.custom_credentials;
    merged.extend(child.network.custom_credentials);
    merged
},
```

`custom_credentials` is a `HashMap<String, CustomCredentialDef>`, so `.extend()` is
**whole-value replace per key**, and `apply_platform_overrides` merges the per-OS block in as
an ordinary `merge_profiles` child. A `platform_overrides.windows` block redefining an existing
credential name **without** `capture` therefore removes the OAuth-capture rewrite for that route
on Windows only — the real token then reaches the sandboxed agent unrewritten. The same channel
drops `spiffe` (route falls back to unauthenticated forwarding).

This contradicts Phase 110's own stated D-08a invariant at `mod.rs:2687-2694` — that an override
"may tighten (add) but never silently loosen" — and it is the odd one out among its neighbours,
all of which are fail-secure-additive: `block` is OR (`:3644`), `deny_domain` / `no_proxy` are
`dedup_append` (`:3653-3654`). Post-override re-validation does not catch it: an override entry
carrying only `credential_key` satisfies the "at least one of" check at `mod.rs:1183-1194`.

### NEW-03 — WARNING — `aws_auth` + `capture` validates but is unreachable
*Affects SEC-01, SEC-02*

`validate_custom_credential` excludes `aws_auth` only against `credential_key`/`auth`, and
`capture` joins no exclusion arm, so the pair loads cleanly. At runtime `reverse.rs:328-331`
returns 501 on `aws_route.is_some()` **before** the capture branch, and the cross-path guards
then deny the same host. Fail-closed, so no leak — but a fully unusable route presenting as
valid config violates "never silently degrade" for an operator-facing control.

### NEW-04 — WARNING — `direct_connect_ports` voids the capture guarantee for granted ports
*Affects NET-01, SEC-02*

`direct_connect_ports` (from `caps.tcp_connect_ports()`, `proxy_runtime.rs:590`) maps to a
sandbox grant that is **port-scoped with no host dimension**. Any profile granting
`--allow-connect-port N` lets the agent open a direct TCP connection to a capture-declared host
on port N without contacting the proxy, so none of Phase 114's three guards can fire. ADR-114's
scope limit covers "CONNECT flows to arbitrary hosts" but does not name this grant as a
mechanism — it should, explicitly.

*Note:* the adjacent NO_PROXY path was traced specifically for this bypass class and is
**correctly closed** — `merge_no_proxy_hosts` (`server.rs:331-360`) re-filters every entry
host-only via `route_host_from_host_port`, so the exact-port `is_route_upstream` at `:705`
cannot leak a capture host into NO_PROXY.

### ACC-01 — ACCURACY — SEC-02's requirement text overstates the delivered surface
*Affects SEC-02*

`REQUIREMENTS.md:131` states the mint-to-resolve loop is "**closed end-to-end** with a live
production call site." That is true only for relay site 1: `resolve_capture_request_body` has
exactly one production call site (`reverse.rs:427-428`), which sits *after* the SPIFFE dispatches
at `:222-247` have already returned. Sites 2 and 3 apply the response relay but not the
request-side resolve. `114-06-SUMMARY.md:131` records this as a deliberate scope limit — but
since `spiffe` + `capture` is both accepted by validation and explicitly supported on the
response side, the requirement record overstates a reachable configuration.

Given this project's twice-burned history with inaccurate records, this is worth correcting to
match ADR-114's more careful Consequence-2 wording.

### New findings

#### NEW-05 — WARNING (security) — the NEW-02 fix left a residual of its own class
*Affects PROF-01, SEC-02*

`merge_custom_credential_def` (`crates/nono-cli/src/profile/mod.rs:3564-3567`) takes three fields
from the child unconditionally:

```rust
upstream: child.upstream,           // :3565 — required field, intended
inject_mode: child.inject_mode,     // :3566
inject_header: child.inject_header, // :3567
```

`inject_mode` is `#[serde(default)]` and `inject_header` is
`#[serde(default = "default_inject_header")]` (`mod.rs:964-972`). A `platform_overrides.<os>` block
that redefines a credential — to change `upstream`, say — and omits both **silently resets** a
`url_path` or `query_param` route to header-mode `Authorization` on that OS. This is the same
removal-by-silence mechanism NEW-02 was about, one tier down: it relocates where the real
credential is injected rather than dropping the capture rewrite.

The fix's own doc comment (`mod.rs:3557-3559`) calls these "presentation fields that remove no
security control." **This finding disputes that.** Where a credential is placed on the wire is not
presentation, and the justification is exactly the shape of reasoning that produced NEW-02. The
counter-argument — that a misplaced credential fails auth rather than leaking — is real but was
never written down or tested. Worth an explicit decision either way.

*Audited and cleared:* the other whole-value-replace `.extend()` maps in `merge_profiles` are not
NEW-02-class. `env_credentials.mappings` (`:3789`) and `environment.set_vars` (`:3804`) are
`HashMap<String, String>` — scalar values, nothing to drop by silence. `hooks.hooks` (`:3820`) is
the one remaining struct-valued map, but `HookConfig` (`:2003-2012`) has three required `String`
fields and no serde defaults, so an override can only swap a whole hook — an explicit statement,
not a silent loss. It is, however, the place a future field addition would re-open NEW-02.

#### NEW-06 — BLOCKER (binding) — nono-py's decoder rejects its own encoder's output
*Affects SEC-02*

- Encoder emits: `../nono-py/src/proxy.rs:99` `"capture_unsupported_path"`, `:102`
  `"capture_buffer_or_rewrite_failed"`.
- Decoder (`../nono-py/src/undo.rs:588-621`) covers 9 variants, ends at `"spiffe_unsupported_path"`
  (`:615`), then `other => Err(PyValueError::new_err(...))`.

So nono-py raises `ValueError: invalid denial_category: capture_unsupported_path` on a dict **its
own encoder produced** — and it breaks on precisely the two denials Phase 114 exists to emit. The
decoder handles `intercept_handshake_failed` and `external_proxy_rejected` (both dead in Rust)
while missing the two live Phase 114 variants, which is the signature of a decoder that was never
updated when 114 landed.

This was already listed as 114 tech debt, scoped open. Recording it here as blocker-class for the
binding, because the audit's own integration section asserted the opposite (ACC-02).

#### NEW-07 — WARNING — nono-py cannot express `capture` or `spiffe` at all
*Affects NET-02, SEC-02*

#### NEW-08 — WARNING — SPIRE JWT-SVID is minted before the deny check
