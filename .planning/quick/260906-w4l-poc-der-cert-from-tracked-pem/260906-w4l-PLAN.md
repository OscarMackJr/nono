# Quick Task 260906-w4l

## Defect

`Windows Build` and `Windows Packaging` both fail at
`scripts/build-windows-msi.ps1:239`:

```
POC DER cert not found at 'D:\a\nono\nono\dist\windows\nono-poc-signing.cer'.
Commit dist/windows/nono-poc-signing.cer to the repo.
```

The script instructs the operator to commit that file. `.gitignore` forbids it,
**twice**:

```
nono-poc-signing.cer      # .gitignore:~105
dist/windows/*.cer        # .gitignore:109
```

So the build demands an artifact the repo is configured to reject. It has been
red for as long as the job has run.

## Root cause: the derivation direction is inverted relative to what is tracked

The script's own comment (lines 229-233) states the intended design:

> The DER .cer (certutil/CryptoAPI format) is committed alongside the scripts.
> The PEM copy (Node-readable for `NODE_EXTRA_CA_CERTS`) is produced from the DER
> cert by `certutil -encode` at build time and committed as nono-poc-signing.pem.

The repository is the mirror image of that:

| File | State |
|---|---|
| `dist/windows/nono-poc-signing.pem` | **tracked** |
| `dist/windows/nono-poc-signing.cer` | **gitignored**, present only on this dev host |

So the file the script treats as the source is the one that does not ship, and
the file it treats as derived is the one that does.

## The two files are the same certificate — verified, not assumed

```
.cer (DER)  subject=CN=nono POC Signing  issuer=CN=nono POC Signing (self-signed)
            SHA1=31:9E:50:7E:95:04:72:D4:90:F5:6F:7C:4C:D9:44:37:C0:13:CC:06
.pem        subject=CN=nono POC Signing
            SHA1=31:9E:50:7E:95:04:72:D4:90:F5:6F:7C:4C:D9:44:37:C0:13:CC:06
```

Identical fingerprint. This is a **public** self-signed POC certificate, already
in the repository in PEM form. No private key is involved and none is being
added — the adjacent `.gitignore` entries that do guard private material
(`*.p12`, `*.pfx.b64`, `*.cert.b64`) are untouched.

## Chosen fix: derive DER from PEM, do not commit a second copy

Invert the fallback so the **tracked** artifact is the source:

- DER present → use it (unchanged; preserves the documented local-dev flow).
- DER absent but PEM present → derive the DER from the PEM at build time.
- Both absent → throw, with a message naming the PEM as the thing to restore.

The existing PEM-from-DER fallback stays, so both directions now work and the
build succeeds whichever file a given checkout happens to have.

**Why not `git add -f` the `.cer` plus a `.gitignore` negation.** It would work,
but it stores the same public key twice in two encodings with nothing enforcing
they stay in agreement — a real drift risk the moment the POC cert is
regenerated. It also punches a special case through a rule that exists for a
good reason: the same block ignores per-release POC certs (`nono-v*-poc.cer`,
`nono-v*.cer`), and a negation invites the next person to add another. Deriving
removes the duplicate entirely and leaves the ignore rule intact.

**Deviation recorded:** this changes the script's stated design (DER as source).
The comment block is updated to describe what the repo actually tracks, so the
next reader is not told the opposite of what is true.

## Implementation

`scripts/build-windows-msi.ps1`, the `if ($Scope -eq "machine")` block:

- Decode with pure PowerShell — read the PEM text, strip the
  `-----BEGIN/END CERTIFICATE-----` armour, `[Convert]::FromBase64String`, write
  bytes. Deliberately **not** `certutil -decode`: the script already worries
  about certutil being absent from PATH (its own line-252 error message says so),
  and a base64 decode needs no external tool.
- Write the derived DER to `dist/windows/nono-poc-signing.cer` — gitignored, so
  it cannot dirty `git status` or be committed by accident.
- Update the lines 229-233 comment to state the real direction.

## Verification

1. **Byte-identity proof.** Derive the DER from the tracked PEM using exactly the
   plan's decode logic, then compare against the real
   `dist/windows/nono-poc-signing.cer` that exists on this host. Must be
   byte-identical — this host holds the genuine artifact CI lacks, so it is a
   true oracle, not a self-consistency check.
2. **Fingerprint match** on the derived file: SHA-1 must equal
   `31:9E:50:7E:95:04:72:D4:90:F5:6F:7C:4C:D9:44:37:C0:13:CC:06`.
3. **Perturbation:** temporarily move the real `.cer` aside, confirm the script's
   resolution block now takes the derive path and produces a valid cert rather
   than throwing; restore.
4. Script still parses as valid PowerShell.

## Constraints

- `dist/windows/*.wxs` is GENERATED by this script — never hand-edit the `.wxs`.
- No private key material is added. Verify the derived file is a certificate
  only (no `PRIVATE KEY` block in the PEM source) before committing anything.
- DCO sign-off on every commit.
