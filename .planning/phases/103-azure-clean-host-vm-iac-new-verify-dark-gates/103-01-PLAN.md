<objective>
Author the first Azure IaC in this repo: a self-contained Bicep module (`main.bicep`) that
declares a Gen2 + Trusted-Launch Windows 11 VM with its own VNet/Subnet/NSG/PublicIP/NIC (RG_Nono
currently has no reusable networking), plus `deploy.ps1`/`teardown.ps1` wrapper scripts that
document and implement the ephemeral create-to-use-to-teardown lifecycle against a dedicated
`RG_Nono_CleanHost` resource group. This is author + local-validate only — no live deploy, no
live Azure resource creation (CHOST-01/SC1; Phase 106 runs these scripts for real).

Purpose: CHOST-01 requires a reproducible, fork-owned clean-host VM that can be stood up and torn
down on demand, with the SKU and NSG scope resolved live (never hardcoded) and the lifecycle
never persistent.

Output: `scripts/azure/clean-vm/main.bicep`, `scripts/azure/clean-vm/deploy.ps1`,
`scripts/azure/clean-vm/teardown.ps1` — all authored, `main.bicep` proven to compile via
`az bicep build`, both PowerShell scripts proven syntactically valid, none of them invoked live.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator workstation → Azure Resource Manager | `az`/Bicep calls carry the operator's live Azure credentials; `main.bicep` declares the entire attack surface of the resulting VM |
| Public Internet → VM RDP endpoint (3389) | The only inbound path this IaC ever opens; scope of exposure is entirely determined by the NSG rule |
| deploy.ps1 → third-party IP-echo services (`ifconfig.me`) | An unauthenticated public HTTP(S) endpoint used only to learn the operator's own IP, never to receive secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-103-01 | Elevation of Privilege / Information Disclosure | `main.bicep` NSG `AllowRdpFromOperator` rule | mitigate | `operatorIpCidr` is a required parameter with no default; RDP is the only inbound rule and it is scoped to that single parameter, never `0.0.0.0/0`; acceptance criteria grep for the literal `0.0.0.0/0` returning 0 |
| T-103-02 | Tampering (of the "clean host" test fixture itself) | Ephemeral VM lifecycle | mitigate | `deploy.ps1`/`teardown.ps1` document and implement create-→use-→teardown against a dedicated `RG_Nono_CleanHost`; `teardown.ps1` blocks (no `--no-wait`) so its own exit proves deletion, never leaving a persistent VM |
| T-103-03 | Tampering / Spoofing (MITM) | Bicep-binary download (Pitfall 1) + operator-IP lookup (Pitfall 2) | mitigate | Both use `curl` over TLS with full certificate validation; `-k`/`--insecure`/any cert-bypass flag is forbidden and grep-checked as 0 occurrences in both scripts |
| T-103-04 | Tampering (silently stale configuration) | `vmImageSku` / `operatorIpCidr` parameters | mitigate | Both parameters have no default value in `main.bicep`; `deploy.ps1` is the only path that can supply them, via live `az vm image list-skus`/`curl` calls, never a hardcoded literal |
| T-103-05 | Information Disclosure | `AdminPassword` secure-string handling in `deploy.ps1` | mitigate | Converted to plaintext only transiently in memory for the single `az deployment group create` call; written to a temp parameters file that is removed in a `finally` block regardless of outcome — never persisted, never logged |
| T-103-SC | Supply Chain (package/binary legitimacy) | Manual Bicep CLI binary download | accept | No npm/pip/cargo install occurs this phase (Package Legitimacy Gate N/A per 103-RESEARCH.md); the Bicep binary is fetched via TLS-validated `curl` from the official `Azure/bicep` GitHub Releases URL, not a third-party mirror |

</threat_model>
