<objective>
Absorb the profile-schema and validation portion of upstream `d5803b99` (#1398): `NetworkConfig`
gains `open_port_range`/`listen_port_range`, `merge_profiles` gains its 3rd exhaustive-literal site
for these fields, and `profile_runtime.rs` gains range validation (start<=end + macOS cumulative
cap). This is the remaining half of PROF-03 not covered by plan 110-03 (library mechanism + Unix
emitters) — the actual profile-facing fields that let an author write `"open_port_range": [[3000,
3999]]` in JSON. This plan does NOT wire `capability_ext.rs` (see plan 110-05) or the Windows WFP
emitter (see plan 110-06).

Purpose: close the gap between "the mechanism exists" (plan 110-03) and "a profile can actually use
it" — without this plan, `localhost_port_ranges` is reachable only by hand-writing Rust, which is not
what PROF-03 asks for.

Output: `NetworkConfig` gains two new `Vec<[u16; 2]>` fields (array-of-pairs, matching upstream's exact
JSON shape — NOT `Vec<(u16,u16)>` tuples, which don't serialize to JSON arrays the way profile authors
expect). `nono-profile.schema.json` gains matching properties (a FORK-ONLY addition — confirmed via
`git show d5803b99 --stat` that upstream's own commit never touched this file, because upstream has no
equivalent strict-schema file; omitting this edit would let the new fields parse via serde but fail
`validate_against_schema()`, exactly the Pitfall 4 trap CONTEXT.md and RESEARCH.md both flag). Range
validation happens once, early, in `profile_runtime.rs`, giving operators a clear parse-time error
instead of a late sandbox-apply-time failure.
</objective>

`NetworkConfig` (verified struct at `profile/mod.rs:1704` today) gains, immediately after the existing
`pub open_port: Vec<u16>` field (verified line 1767):
```
/// Inclusive port ranges for bidirectional localhost TCP IPC (connect + bind).
/// Multiple ranges are supported. Example: [[3000, 3010], [8000, 8100]].
/// Each port becomes an individual rule — larger ranges take longer to apply at startup.
/// macOS enforces a combined limit of 16,384 unique ports across all ranges (2^14);
/// Linux has no such restriction. Overlapping ranges are merged before applying rules.
#[serde(default)]
pub open_port_range: Vec<[u16; 2]>,
```
and immediately after the existing `pub listen_port: Vec<u16>` field (verified line 1771):
```
/// Inclusive port ranges for TCP listen (bind only). Same platform behaviour as
/// open_port_range for the bind side; no outbound connect rules are added.
/// Overlapping ranges are merged before applying rules.
#[serde(default)]
pub listen_port_range: Vec<[u16; 2]>,
```

the SAME `dedup_append` union pattern as every sibling field:
```
open_port_range: dedup_append(&base.network.open_port_range, &child.network.open_port_range),
...
listen_port_range: dedup_append(&base.network.listen_port_range, &child.network.listen_port_range),
```
placed immediately after `open_port:`/`listen_port:` respectively (matching upstream's exact
placement).

The two existing test-fixture `NetworkConfig { ... }` exhaustive literals inside `mod tests` (verified
present, e.g. containing `open_port: vec![3000]` / `open_port: vec![3000, 5000]`) each need
`open_port_range: vec![],`/`listen_port_range: vec![],` added — the compiler will name the exact line
numbers as build errors once the fields exist.

profile_runtime.rs — inside `prepare_profile_with_options` (verified function, diff lands right before
the function's final `Ok(PreparedProfile { ... })` return), add, guarded by `if let Some(profile) =
loaded_profile.as_ref()`:
1. A start<=end check over BOTH `open_port_range` and `listen_port_range` entries — for each `[start,
   end]` where `start > end`, return `Err(nono::NonoError::ProfileParse(format!("{label} entry [{start},
   {end}] is invalid: start must be <= end")))` where `label` is `"open_port_range"` or
   `"listen_port_range"` respectively (loop over both fields via a small `[(label, slice); 2]` array,
   matching upstream's exact shape).
2. `#[cfg(target_os = "macos")]`-gated: merge BOTH fields' ranges independently via
   `nono::capability::merge_port_ranges`, sum their combined port counts, and if the total exceeds
   `nono::capability::MACOS_PORT_RANGE_LIMIT`, return the same "exceeds the macOS limit" error shape
   used inside the sandbox emitter (plan 110-03) — this is a deliberate, upstream-authored
   defense-in-depth duplication (the sandbox layer checks again too), not dead code.

The existing `listen_ports: loaded_profile.as_ref().map(|profile|
profile.network.listen_port.clone()).unwrap_or_default(),` field inside the `PreparedProfile { ... }`
literal (verified around line 838-841 today) is REPLACED with a block that starts from the same
discrete `listen_port.clone()` base, then for each MERGED `listen_port_range` entry, checks `start ==
0` (return `Err(nono::NonoError::ConfigParse("listen_port_range entry starting at 0 is invalid; port 0
has no defined meaning in a range".to_string()))` if so) and otherwise does `ports.extend(start..=end)`
— i.e. `listen_port_range` unrolls into DISCRETE ports appended to the SAME `listen_ports: Vec<u16>`
list the profile's `listen_port` field already populates, NOT into a new CapabilitySet field. This is
confirmed exact upstream behavior (`git show d5803b99 -- crates/nono-cli/src/profile_runtime.rs`) —
do not invent a `listen_port_ranges` CapabilitySet field, none exists.

`open_port_range` does NOT get this same treatment — it flows to `CapabilitySet.localhost_port_ranges()`
via `capability_ext.rs` instead (plan 110-05's scope, not this plan's).
