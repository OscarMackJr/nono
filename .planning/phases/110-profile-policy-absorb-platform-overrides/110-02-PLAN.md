Absorb upstream `2cbaa9a0` (#1296, generic `$VAR` process-env expansion) and `d4927f95` (#1298,
`@git:*` dynamic-token expansion in the top-level filesystem lists) — scoped per CONTEXT.md D-01/D-02/

git-aware tokens directly in `filesystem.allow`/`read`/etc., matching the behavior tool-sandbox
per-command sandboxes already have — without pulling the (absent, deferred-to-v3.7) `tool-sandbox`
subsystem forward.

`expand_dynamic_tokens` function (git-token dispatch + the global/system-scope-only git-config
restriction) with its own ~32-test suite, cfg-gated so it compiles identically on Linux/macOS/Windows.
`policy.rs` gains the generic `substitute_vars`/`expand_env_vars` engine. `capability_ext.rs` gains a
distinctly-named `expand_profile_path` wrapper (avoiding a name collision with the pre-existing,
differently-signatured `crate::policy::expand_path`) and wires `expand_dynamic_tokens` ahead of it at
exactly the 8 call sites upstream's `d4927f95` diff touches.

**MANDATORY v3.7 reconciliation note (D-02):** `expand_dynamic_tokens` is ported here as a
fork-owned, standalone copy — NOT under a `crate::tool_sandbox` path (that module does not exist in
this fork and must not be created). When v3.7 (Windows Tool-Sandbox Parity) eventually absorbs the
`tool-sandbox/` subsystem, it MUST reconcile this early-arriving copy (adopt this module's
implementation as the shared one, or replace it and delete `dynamic_tokens.rs`) rather than silently
introducing a second, divergent copy of the same git-token logic. Record this note verbatim in the
plan's SUMMARY.

  use crate::dynamic_tokens::expand_dynamic_tokens;

  // Expand a profile path template: arbitrary $VAR tokens from the process
  // environment are resolved first, then built-in nono vars ($HOME, $WORKDIR,
  // $TMPDIR, $XDG_*, etc.) are applied. Named distinctly from
  // crate::policy::expand_path (different module, different signature,
  // different purpose) to avoid a same-name footgun.
  fn expand_profile_path(template: &str, workdir: &Path) -> nono::Result<PathBuf> {
      let after_env = policy::expand_env_vars(template);
      expand_vars(&after_env, workdir)
  }

  #[cfg(not(any(target_os = "linux", target_os = "macos")))]
  fn expand_dynamic_tokens(entries: &[String], _workdir: Option<&Path>) -> nono::Result<Vec<String>> {
      Ok(entries.to_vec())
  }

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| profile JSON (operator-authored) -> capability_ext.rs expansion pipeline | Untrusted path templates containing `$VAR`/`@git:*` tokens are expanded before becoming filesystem capabilities |
| sandboxed workdir's git state -> expand_dynamic_tokens | The dynamic-token resolver shells out to `git` scoped to the sandboxed workdir; a hostile or crafted repo under that workdir must not be able to widen the grant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-110-04 | Tampering / Information Disclosure | `dynamic_tokens.rs::parse_paths_from_stdout` | mitigate | only `global`/`system` git-config scopes are honored (`TRUSTED_SCOPES`); `local`/`worktree` scope entries are explicitly dropped, so a hostile per-repo `.git/config` cannot inject a path — ported unmodified with its own regression test `git_read_paths_excludes_per_repo_local_config_overrides` |
| T-110-05 | Tampering | `dynamic_tokens.rs::dispatch_token` (unknown provider/query) | mitigate | unknown token dispatch returns an explicit error (fails closed on typos), ported verbatim from upstream's own stated design goal |
| T-110-06 | Elevation of Privilege | `capability_ext.rs` non-Unix cfg fallback | mitigate | on Windows the fallback `expand_dynamic_tokens` returns entries unchanged (no dynamic-token feature, not a silent grant-widening) — matches upstream's own documented non-Unix behavior |
| T-110-SC | Tampering | npm/pip/cargo installs | mitigate | zero new external dependencies (confirmed via `git show --stat` on both source commits) |
</threat_model>
