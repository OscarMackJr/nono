<objective>
Write the Windows WFP-native remote-port-range emitter. Implements the Windows arm of PROF-03. Unlike
every other plan in this phase, this is FORK-ORIGINAL enforcement code (D-07) — upstream implemented
only macOS and Linux emitters for `d5803b99`; there is no upstream diff to port here. This is the
first genuinely new kernel-facing surface in the v3.6 milestone.

Purpose: give Windows the same port-range capability as macOS/Linux, but expressed NATIVELY via WFP's
`FWP_MATCH_RANGE` condition type — a single filter object per range regardless of width, never
unrolled into per-port filters the way Seatbelt is forced to (D-06). This is materially more efficient
than either Unix backend and needs neither `MACOS_PORT_RANGE_LIMIT`'s cap (that cap exists solely
because Seatbelt turns every port into an individual rule) nor Linux's per-port loop.

Output: `sandbox/windows.rs::compile_network_policy` (library, policy-free — reads `CapabilitySet`,
produces a `WindowsNetworkPolicy` value) gains a `localhost_port_ranges` field. The general,
non-daemon-gated Windows network pipeline (`compile_network_policy` -> `prepare_network_enforcement`,
invoked from the ordinary `nono run` supervised-exec dispatch at `exec_strategy_windows/mod.rs:484` —
NOT the narrower `agent_daemon/launch.rs::wfp_filter_add` daemon-only path) threads the new field
through `WfpRuntimeActivationRequest` to `nono-wfp-service.rs`'s already-tested, pure filter-spec
builder, which gains two new `PortCondition` variants and a `FWP_MATCH_RANGE`-based construction arm
using types already present in the pinned `windows-sys 0.59` dependency (`FWP_MATCH_RANGE`,
`FWP_RANGE0`, `FWP_VALUE0` — confirmed in the vendored crate source, zero new dependencies).

This plan's final task is a `checkpoint:human-verify` for the live-kernel arm (PROF-03e), since
`FwpmFilterAdd0` cannot be exercised from a non-elevated, non-Administrator dev session — this makes
the plan `autonomous: false`.
</objective>
