New functions (exact signatures from the diff, port verbatim):
```
fn rewrite_absolute_to_origin_form(line: &str) -> Result<String>
fn strip_proxy_headers(header_bytes: &[u8]) -> Vec<u8>
    // removes ONLY Proxy-Connection/Proxy-Authorization headers; Host and all other headers
    // pass through verbatim so the forwarded request matches what the client sent
async fn handle_forward_http(
    first_line: &str,
    stream: &mut TcpStream,
    header_bytes: &[u8],
    buffered: &[u8],
    state: &ProxyState,
) -> Result<()>
```
`handle_forward_http`'s documented steps (port the doc comment's security rationale verbatim — it
is load-bearing, not decorative):
1. Enforce `Proxy-Authorization` (same session-token gate as CONNECT/reverse) — 407 + audit denial
   on failure, matching the reverse path's no-credential branch.
2. Parse host+port from the absolute URL, run the host filter (`filter.check_host`) — 403 +
   `HostDenied` audit event on deny, mirroring the CONNECT path's inline `else`.
3. Rewrite the request line to origin-form (`rewrite_absolute_to_origin_form`), strip hop-by-hop
   proxy headers (`strip_proxy_headers`), forward via the shared L7 pipeline using the
   DNS-rebinding-safe resolved addresses `check_host` already returned (or the external proxy
   chain) — connect to the RESOLVED addresses, never re-resolve the hostname.
   IMPORTANT (documented in the upstream source, preserve verbatim as a doc comment): this path
   intentionally does NOT call `reverse::validate_http_upstream_target` (which enforces
   loopback-only for reverse-proxy `http` upstreams) — a general forward proxy exists precisely to
   reach arbitrary ALLOWED `http://` hosts on the agent's behalf; `check_host` is the sufficient and
   authoritative trust boundary here, not the loopback-only reverse-proxy assumption.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| absolute-form HTTP client -> forward-proxy handler | A new serving path accepting arbitrary absolute-form URLs from the sandboxed child, distinct from the existing CONNECT tunnel and reverse-proxy paths |
| forward-proxy path -> credential store | Must NOT share the reverse-proxy's credential-injection behavior even when the target host has a configured managed-credential route |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-109-10 | Spoofing / Elevation of Privilege | `handle_forward_http` request-line rewrite | mitigate | dispatch ordering places the absolute-form check BEFORE `parse_service_prefix`/reverse-proxy dispatch (issue #1334 regression this fix addresses), preventing an absolute URL from being misread as a reverse-proxy service prefix |
| T-109-11 | Elevation of Privilege | Denied-host absolute-form request | mitigate | `handle_forward_http` runs the SAME `filter.check_host` trust boundary as the CONNECT tunnel — no new bypass path; `forward_http_denied_host_returns_403_and_audits` proves the 403+audit contract |
| T-109-12 | Information Disclosure / Elevation of Privilege | Credential injection on a forwarded request | mitigate | `forward_http_does_not_inject_managed_credential` proves the forward-proxy path never injects the reverse-proxy's managed credentials, even for a host that has a configured credential route |
| T-109-13 | Denial of Service | Absolute-form `https://` requests | mitigate | rejected with explicit 400 + CONNECT guidance rather than attempting cleartext-forward of what the client intended as TLS, or a confusing 502 |
| T-109-SC | Tampering | npm/pip/cargo installs | mitigate | no new external dependencies introduced by this plan; single-file additive Rust code |
</threat_model>
