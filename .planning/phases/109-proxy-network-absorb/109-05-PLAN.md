**#1430 (`6fb7ecbf`, SigV4 encoded-URI fix) evidence:**
- Upstream diff touches exactly `crates/nono-proxy/src/aws/sign.rs` (20 lines changed inside
  `pub async fn sign_request`), adjusting `PercentEncodingMode`/`UriPathNormalizationMode` per-service
  (S3 vs non-S3).
- The fork has NO `crates/nono-proxy/src/aws/` directory at all (`Glob crates/nono-proxy/src/aws/*.rs`
  returns no files).
- The fork's `CredentialStore` (`crates/nono-proxy/src/credential.rs`) carries `aws_routes:
  HashMap&lt;String, ()&gt;` explicitly documented as "a placeholder until full SigV4 signing is
  implemented; value is () because no runtime state is needed yet" — `get_aws()` returns
  `Option&lt;&()&gt;`, not a real signing route.
- `crates/nono-proxy/src/reverse.rs` (~line 260-266) returns HTTP 501 for any AWS SigV4 route with
  the comment "AWS SigV4 signing is not yet implemented... upstream's 501 is in
  tls_intercept/handle.rs which the fork does not [have]" — this is a PRE-EXISTING, already-decided
  fork posture from a prior phase, not new information this plan introduces.
- `grep -rn "hmac\|sha256\|canonical_request\|StringToSign" crates/nono-proxy/src/` returns zero
  signing-algorithm hits anywhere in the crate.

**#1437 (`23d93fc9`, sibling-route cross-deny fix) evidence:**
- Upstream diff touches exactly `crates/nono-proxy/src/tls_intercept/handle.rs`'s
  `select_intercept_route` function (a multi-route-per-upstream-host TLS-intercept dispatcher).
- The fork has NO `crates/nono-proxy/src/tls_intercept/` directory at all.
- The fork's `CredentialStore` doc comment (`crates/nono-proxy/src/credential.rs`, ~line 104-109)
  states explicitly: "2-match-deny — structurally impossible in this store. The upstream 'ambiguous
  selection' case only arises when multiple routes share an upstream host AND the inner-request path
  can match more than one route's `endpoint_rules`. Both preconditions require the TLS-intercept
  multi-route dispatch surface that the fork does not have."
- `crates/nono-proxy/src/server.rs` (~line 296-298) independently confirms the same architectural
  fact: "[TLS trust intent] WITHOUT pulling in the tls_intercept module (per D-40-B2 fork-preserve
  lock; fork has no tls_intercept)."
- The fork's actual route dispatch (`crates/nono-proxy/src/reverse.rs::handle_reverse_proxy`) is
  single-route-per-path-prefix (`RouteStore::get(&service)` via `HashMap`), architecturally
  incapable of the sibling-route ambiguity `#1437` fixes — there is no "first route by prefix order"
  concept in the fork's dispatch, so the bug class does not exist here.

**Conclusion (Task 1 re-verifies, does not merely restate):** both fixes are bug fixes to upstream
subsystems (full AWS SigV4 signing, TLS-intercept multi-route dispatch) that were deliberately never
absorbed into the fork in an earlier phase, and remain absent. There is no code in the fork these two
patches apply to. "Absorbed" for these two items means "confirmed non-applicable, with evidence,"
not "code changed" — implementing either missing subsystem from scratch would be an unrelated,
much larger net-new feature, not a 16-line/87-line bug-fix absorb, and is explicitly out of this
phase's scope (NET-02/SPIFFE — the phase's other TLS-intercept-adjacent item — was already split to
Phase 113 for exactly this reason: it is a refactor of a subsystem the fork does not have in the
upstream shape).
