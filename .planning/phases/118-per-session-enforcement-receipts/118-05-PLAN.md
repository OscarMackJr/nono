<objective>
Build the dedicated, operator-ACL'd receipt sink (D-06) that both `nono.exe` and `nono-agentd.exe`
write through — the primary channel RCPT-02's governance consumer actually retrieves from, since
D-07's live measurement did not clear the Windows Event Log readability assumption either way.
Apply D-08's both-not-either guard (DENY ACE + NO_READ_UP label) using Plan 118-02's new primitive
plus the existing mandatory-label wrapper. Give each writer its own mutex-guarded, KEYLESS
(D-25) chain-advance state, mirroring `advance_and_emit`'s WR-21/WR-09 discipline without the
ephemeral-key lifecycle.

Purpose: this is the shared plumbing Plans 118-07 (nono.exe wiring) and 118-08 (nono-agentd
wiring) both call — building it once, in a module reachable from both real call graphs, avoids the
`dead_code` double-compilation trap (critical constraint 5).
Output: `crates/nono-cli/src/receipt_sink.rs`, wired into both binaries via `main.rs`'s normal
`mod` declaration and a new `#[path]` line in `nono-agentd.rs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Confined child (same user as supervisor) → sink directory | The central D-08 constraint: an ordinary DACL cannot separate same-user processes; both mechanisms are required together. |
| `receipt_sink.rs` → both binaries' real call graphs | If this module is ever called by only one binary, the other's compilation trips a `dead_code` lint that neither `#[expect]` nor a feature flag can fix (critical constraint 5) — this plan's design keeps it genuinely dual-called by construction (118-07 and 118-08 both add real call sites). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-118-14 | Information Disclosure | Confined child reading the receipt sink for reconnaissance | mitigate | DENY ACE (session SID + package SID) PLUS `NO_READ_UP` mandatory label — both, unconditionally applied on directory creation (D-08). Manual confined-child verification is a checkpoint in Plan 118-10, since it cannot be proven by a unit test alone (supervisor and child share a user). |
| T-118-15 | Tampering | Sink directory ACL/label application failing silently | mitigate | `write_receipt`/`ensure_sink_guarded` return `Err` on any failure, never panic and never silently proceed unguarded — the caller (118-07/08) is responsible for D-04's visible-degrade behavior around this `Err`. |
| T-118-16 | Repudiation | Windows Event Log being treated as authoritative when its readability is unproven (D-07) | accept (documented) | D-06 makes this plan's design independent of the Event Log question entirely — the dedicated sink is primary; the Event Log (if used at all, per the discretion item) is at most a coarse pointer, never load-bearing for RCPT-02's tamper-evidence claim. |
| T-118-17 | Tampering | Chain-advance and file-write happening under separate locks, allowing an interleaved write to corrupt sequence ordering | mitigate | `write_receipt` holds one mutex across build+advance+write (WR-21 discipline, mirrored from `advance_and_emit`), never releasing the lock between chain-state update and the on-disk append. |
</threat_model>
