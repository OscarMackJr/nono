<objective>
Wire the daemon's now-complete 13-row census (D-01) (Plan 118-04's restructured `daemon_attest_and_decide`
+ expectancy table) into the shared receipt sink (Plan 118-05) at the daemon's own attestation
gate call site, so every `nono agent launch` session produces a real receipt. This is the daemon-arm
half of D-15's "whoever attests, writes" rule — `nono-agentd` has no parent `nono.exe` to report
back to, so it must write its own receipt directly.

Purpose: without this plan, the daemon path (a genuinely independent supervisor for daemon
sessions, per D-15) would have a complete census (from 118-04) with nowhere to go.
Output: the daemon's gate calls `build_daemon_receipt` + `write_receipt` on both branches; a
documented triage note if any `Unconfirmed`-on-`Proceed` row is observed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `nono-agentd` is its own supervisor — no parent `nono.exe` | Unlike the DirectCli/broker arms, there is no second process to cross-check the daemon's own receipt against; the daemon's honesty depends entirely on this plan's wiring being correct. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-118-24 | Repudiation | Daemon session id not being genuinely opaque (e.g. derived from a workspace path if no existing session-id mechanism is found) | mitigate | Task 1 requires generating a fresh opaque id at session start if none exists — explicitly forbidding a path-derived fallback, per D-05. |
| T-118-25 | Repudiation | `Unconfirmed`-on-`Proceed` rows getting silently ignored rather than triaged | mitigate | Task 2 requires an explicit, recorded finding either way — this is the D-16 requirement made into a concrete, checkable deliverable rather than a hope. |
| T-118-26 | Denial of Service | Daemon sessions (long-running, multi-tenant per MEMORY's `nono-agentd` history) each writing a receipt under load | accept (documented) | Plan 118-05's `ReceiptWriter` already holds its mutex only across a single build+advance+write sequence (not across the whole session) — no design change needed here; if daemon-session receipt-write latency proves material, that is a D-17-adjacent measurement question for a later finding, out of this plan's scope. |
</threat_model>
