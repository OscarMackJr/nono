## Scope note

Phase 114 is a proxy-internals security phase. Most of what it built — the response
buffer-and-rewrite enforcement point, the phantom store, the cross-path guard — has **no manual
surface**: exercising it end-to-end needs a live OAuth provider and a sandboxed agent completing a
real login. That behaviour is covered by automated tests (300 lib + 5 integration in
`nono-sandbox-proxy`, including a live-dispatch e2e test asserting the real token reaches upstream
and the phantom does not), by the orchestrator's hand control-flow audit
(`114-05-SUMMARY.md`), and by the code review that found and closed 3 Criticals (`114-REVIEW.md`).

What IS manually observable is the **declarative operator interface**: writing a `capture` block in
a profile and having nono accept it, reject it clearly when malformed, and never silently drop it.
That is what these tests cover. Fixtures live in the session scratchpad; paths are given per test.

All commands below use `./target/debug/nono.exe` — the release binary predates this phase's fixes
and is stale.

  missing:
    - "`#[serde(deny_unknown_fields)]` on `CaptureConfig` and `CaptureResponseField`"
  root_cause: |
    DIAGNOSED — this is a Phase-114-introduced inconsistency, not an inherited repo-wide gap.

    `nono profile validate` never invokes `validate_against_schema()`; its only call sites are
    `profile/mod.rs:7388/7399/7409`, all inside the `#[cfg(test)]` module. So the shipped JSON
    Schema's `additionalProperties: false` is documentation, not enforcement — in production the
    real mechanism is serde's `#[serde(deny_unknown_fields)]`.

    The sibling types in the custom-credential tree DO carry it: an unknown key at
    `CustomCredentialDef` level is rejected with "unknown field `bogus_unrelated_key`, expected
    one of `upstream`, ..., `capture`". Phase 114's new `CaptureConfig` (config.rs:719) and
    `CaptureResponseField` (config.rs:704) omit it, so they are the only types in that tree that
    silently swallow unknown keys.

    Severity is major, not blocker: no security property is bypassed, and the load-bearing case
    IS caught — Test 3 confirms a typo'd `response_fields` is rejected because
    `validate_capture_config()` independently rejects an empty field list. The defect is that a
    key which sounds security-relevant (`persist_to_disk`, asserting the opposite of D-08) is
    accepted with `Result: valid`, so an operator can hold a false belief about what the config
    does. That is the same "advertises capability it does not have" shape D-13 exists to prevent.

    Fix: add `#[serde(deny_unknown_fields)]` to both structs, plus a regression test asserting an
    unknown capture key is rejected. Check `CaptureResponseFieldKind` too.
