<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| profile author -> profile/mod.rs parser+merger | A profile (base + `platform_overrides.<os>`) is semi-trusted config; the merge logic decides where a credential is injected on the wire |
| merged CustomCredentialDef -> nono-proxy RouteConfig | network_policy.rs's conversion is the sole production bridge between CLI policy and proxy enforcement |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-115-01 | Tampering | `merge_custom_credential_def` | mitigate | `Option<T>` + `.or(base)` makes an override that omits `inject_mode`/`inject_header` inherit the base instead of silently resetting to header/Authorization; exhaustive test (Task 2) is the regression gate, proven load-bearing by revert-and-confirm; the `InjectMode` -> `Option<InjectMode>` type change also makes a missed consumer site a **compile failure**, not a silent wire-placement change — this is exactly why D-01 chose the type change over deserialize-time key tracking |
| T-115-02 | Information Disclosure | doc comment above `merge_custom_credential_def` | mitigate | D-05 corrected comment removes the "presentation fields" framing that justified NEW-05, preventing a future engineer from reintroducing it under the same false premise |
| T-115-03 | Tampering | `HookConfig` / `merge_profiles` hooks merge | mitigate | compile-time exhaustive-destructure guard (D-04), live bite-proof verified — a future field addition cannot silently be dropped by the whole-value-replace merge |
</threat_model>
