    - `deny_suffixes: Vec<String>` field on `HostFilter` (parallel to existing `deny_hosts`)
    - `pub fn with_denied_hosts(mut self, denied: &[String]) -> Self` builder — splits entries
      on a leading `*` into `deny_suffixes` vs exact `deny_hosts`; caller-supplied, not
      hardcoded (this is what keeps it ADR-86-compliant: policy stays caller/CLI-side)
    - `check_host()` gains a "1b. Check deny suffixes (wildcard match)" step, evaluated

<!-- Current fork state of crates/nono/src/net_filter.rs (verified 2026-07-29, before any #1374
     absorb): -->
    - `HostFilter` already has `deny_hosts: Vec<String>` + hardcoded `DENY_HOSTS` (cloud-metadata
      addresses) + `strict: bool` field + `FilterResult::Deny`-family variants (`DenyHost`,
      `DenyLinkLocal`, `DenyNotAllowed`)
    - `HostFilter::new()` and `HostFilter::allow_all()` both construct with `strict: false`
    - `check_host()`'s step "3. Empty allowlist: deny when strict, allow otherwise" — quoting the
      current inline comment verbatim — means: if `strict == false` (the default) and the
      allowlist (`allowed_hosts`/`allowed_suffixes`) is empty, the filter returns
      `FilterResult::Allow`. A profile that configures ONLY `deny_domain` entries (no
      `allow_domain`) produces exactly this state: empty allowlist + `strict: false` →
      default-allow, weakening NET-01's "compose without weakening default-deny" requirement.
    - `HostFilter::new_strict(allowed_hosts: &[String])` exists and sets `strict: true`, but
      nothing in the current fork wires deny-only configuration to select it.
