<objective>
Close two independent "class coverage" findings from iteration 5 — a fix applied to one site of a
class while a sibling site of the same class stayed broken:

- **WR-17:** `render_error_for_operator`'s remediation line (`main.rs:247-257`, added by Plan
  117-21 for WR-04) names `nono setup --check-only` for EVERY `LayerAttestationFailed`, regardless
  of which layer failed. That command runs `print_check_only_summary` (`setup.rs:1315-1336`), which
  performs no mandatory-label inspection on any policy path — an operator hitting the
  `MandatoryIntegrityLabel` stale-residue abort follows the instruction and sees "Installation
  verified!" with no closer diagnosis. The core crate already knows the real remedy
  (`codes.rs:74-79`'s doc comment: `icacls <path> /setintegritylevel Medium`) and it never reaches
  the operator. Worse, the same hardcoded line now fires for `WfpEgressFilters`,
  `AppContainerProfile`, `JobObjectContainment`, or a forced-unavailable-seam abort — a wrong lead
  for four of the five layers that can produce this error.
- **WR-18:** CR-01 widened `low_integrity_label_ace` to read `header.AceFlags` and reject
  `INHERIT_ONLY_ACE`, but `low_integrity_label_rid` — the function directly above it in the same
  file, walking the same SACL, filtering the same `SYSTEM_MANDATORY_LABEL_ACE_TYPE` — was not
  touched. Its one production consumer, `is_low_integrity_compatible_dir` (exported as
  `Sandbox::windows_supports_direct_writable_dir`), still reports a directory carrying only an
  inert `S:(ML;OICIIO;…;LW)` ACE as label-compatible — CR-01's exact defect, one function over, in a
  public library API consumed by the C/Python/TypeScript bindings.

Purpose: finish CR-01's class (every mandatory-label ACE reader, not just one) and WR-04's class
(every layer's remediation text, not just one hardcoded command).
Output: layer-specific remediation branching in `main.rs`; `low_integrity_label_rid` delegating to
the already-widened `low_integrity_label_ace`.
</objective>
