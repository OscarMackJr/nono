<objective>
Close WR-30 — `advance_and_emit`'s "Deadlock analysis" doc comment states a false premise. It
justifies holding the chain mutex across the `emit` closure call by claiming `emit_security_event`
"writes to the Windows Application log / ETW and touches no `SecurityEventLayer` state, so it
cannot re-enter this mutex." In fact `emit_security_event` emits a real `tracing` event via
`tracing::warn!(target: "nono_security", ...)`, and `SecurityEventLayer` IS a registered `Layer` on
the global subscriber whose `on_event` takes `self.inner`'s lock. The only reason this does not
self-deadlock today is two mechanisms the comment never names: (1) `on_event` returns early unless
`event.metadata().target().starts_with("nono_security::")` — and the emit target is the BARE string
`"nono_security"`, with no trailing `::`, so the prefix test misses by two characters, purely
incidentally; (2) `tracing`'s per-thread dispatch does not apply here since `advance_and_emit` is
not itself inside a subscriber callback. Every doc comment in this module describes the target
convention as `nono_security::*` (module doc, `windows.rs:170,191`) — a future edit that "fixes"
the emit target to match that documented convention flips this from safe to a self-deadlock, where
the supervisor hangs holding a `CREATE_SUSPENDED` child that is never resumed or terminated. A hang
here is strictly worse than a crash.

Purpose: correct the doc comment to state the real invariant, and enforce it mechanically so a
future edit that aligns the target string with the module's own stated convention fails the build
instead of silently introducing a supervisor hang.
Output: corrected `advance_and_emit` doc comment; a new source-text regression test pinning the
real safety invariant.
</objective>
