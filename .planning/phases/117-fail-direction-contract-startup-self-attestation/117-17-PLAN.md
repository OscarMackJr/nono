<objective>
Close NR3-05 — `DaemonAttestationDecision::ProceedDowngraded` is declared and matched in a ~60-line
arm (`launch_agent`, lines ~915-973) but has NO constructor anywhere in the shipped daemon binary
(`daemon_attest_and_decide` only ever returns `Proceed` or `Abort`). This is dead code: the arm's
audit emission, dedup key, and Event Log warning never fire. It also diverges silently from the
CLI's genuinely three-state model (`Proceed` / `ProceedDowngraded` / `Abort`), which the module's
own doc comment (line ~889) claims to mirror.

The review offers two equally valid fixes: wire a real coverage accessor into `DaemonDaclGuard` so
`ProceedDowngraded` becomes reachable (mirroring `DaclGrantCoverage::application()`'s shape), or
delete the dead variant and document the daemon path as deliberately abort-or-proceed. This plan
takes the DELETION path: every layer `daemon_attest_and_decide` currently models
(`AppContainerProfile`, `JobObjectContainment`, `WfpEgressFilters`, `DaclPackageSidGrant`) already
has NO representable partial-coverage state in the daemon's own guards today (`DaemonDaclGuard`'s
three-pass apply is fail-closed end-to-end, per NR-05's own "honest limits" section) — so wiring a
downgrade path would add tracking machinery for a state that still cannot occur, while deletion
removes genuinely dead code and makes the daemon's actual (stricter, abort-or-proceed) posture
provable rather than merely narrated.

Purpose: dead code that claims to model a state it cannot produce is itself a small instance of the
"reports a capability it does not have" class CINT-02 exists to eliminate — the fix must make the
gap either real or gone, never left declared-but-unreachable.
Output: `DaemonAttestationDecision` becomes a genuinely two-state enum; the module doc is corrected;
a discovery-based test protects the deliberate two-state design from silently drifting.
</objective>
