<objective>
Close WR-25 and WR-34 — the two remaining ways the CR-01 `INHERIT_ONLY_ACE` hardening fails to
cover the mandatory-label ACE family as a class.

**WR-25.** WR-18's SPEC ledger row claims: *"Enumerated every `SYSTEM_MANDATORY_LABEL_ACE` reader
in the workspace; confirmed exactly these two exist and both now share one implementation."* This
planning session re-ran the enumeration independently
(`grep -rn "low_integrity_label_and_mask\|low_integrity_label_ace\|low_integrity_label_rid\|INHERIT_ONLY_ACE" crates/ bindings/`)
and the claim is inaccurate. There is exactly ONE SACL walk — `low_integrity_label_ace`
(`windows.rs:2011`, `pub`, re-exported at `lib.rs:97`) — and **three** consumers of what it
returns:

| consumer | filters `INHERIT_ONLY_ACE`? | evidence |
|---|---|---|
| `low_integrity_label_rid` → `is_low_integrity_compatible_dir` | yes | `windows.rs:1994-1996` |
| `labels_guard.rs`'s residue predicate | yes (CR-01) | `labels_guard.rs:284`, `:304` |
| `low_integrity_label_and_mask` (`pub`, re-exported) | **no** | `windows.rs:2110-2111` |

The third drops `_flags` on the floor, so a structurally-inert inherit-only ACE is
indistinguishable from an effective one — CR-01's exact class, at the **public API boundary**,
where `nono-py` / `nono-ts` / the C FFI inherit it. Its in-tree production consumer
(`hook_runtime_windows.rs:590`) only emits a warning, which is why this is a Warning; the
enumeration claim in the ledger is wrong regardless.

**WR-34.** `plant_mandatory_label_with_flags` exists twice — `windows.rs:3281` and
`labels_guard.rs:827` — as byte-similar ~80-line `unsafe` Win32 helpers in separate crates.
`windows.rs:3275`'s own doc comment already admits it was copied *"verbatim from `nono-cli`'s
`labels_guard.rs::plant_mandatory_label_with_flags`"*, so the duplication is known and
unguarded. CR-01/WR-18's hardening is only meaningful if both crates' tests plant the SAME ACE
shape; a fixture change applied to one will not reach the other, and nothing fails when they
drift.

**A correction to the review's prescribed remedy for WR-34.** It proposes promoting the helper
into `nono` behind a `#[cfg(feature = "test-support")] pub` module, *"mirroring the existing
`layer-fault-injection` feature-gating precedent."* That precedent is **not in `nono`** — this
planning session read both manifests: `layer-fault-injection` is declared at
`crates/nono-cli/Cargo.toml:48`, and `crates/nono/Cargo.toml`'s `[features]` contains only
`default = ["system-keyring"]` and `system-keyring`. Worse, `nono-cli` consumes `nono` with
`default-features = false` (`crates/nono-cli/Cargo.toml:51`), so the feature route requires a
duplicate dev-dependency entry to enable it for tests, and adds a `pub` surface to a published
security crate purely for test scaffolding. This plan therefore **defaults to the review's own
stated fallback** — a mechanical source-text sync gate — and requires an explicit written
rationale before the feature route may be chosen instead.

Purpose: make CR-01's hardening a property of the label-read CLASS with a gate that catches the
next consumer, rather than a fix applied to whichever consumers were remembered.
Output: a hardened `low_integrity_label_and_mask`; a consumer-enumeration gate; a sync gate on
the duplicated planting helper; a corrected WR-18 ledger row.
