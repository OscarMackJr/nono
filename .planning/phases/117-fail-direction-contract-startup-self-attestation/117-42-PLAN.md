<objective>
Close WR-23 and WR-24 — the two ways `log_target_is_private()`'s documented fail-secure rule is
not implemented by its own data model.

**WR-23 (fail-open, real).** The doc comment at `cli_bootstrap.rs:68-70` states the rule:
*"Fail-secure on every unknown/error case (WR-16's own stated rule): no `--log-file` arm selected,
**no granted-path check has run**, or the stored log path fails to canonicalize all return
`false`"*. The middle clause cannot be implemented: `GRANTED_READ_PATHS` is
`Mutex<Vec<PathBuf>>` initialised to `Vec::new()` (`:49`), with nothing distinguishing "never
populated" from "populated empty". The final expression is `!granted_paths.iter().any(..)`
(`:107-115`) — on an empty vec that is `!false` = **`true` ("private")**, so the D-28 gate OPENS
for any path reaching it before `set_granted_read_paths` has run. Today the only production
consumer is `spawn_windows_child` (writes at `launch.rs:1647-1649`, reads at `:1501`), so the
ordering happens to hold — but the safety rests on an unstated single-call-site invariant that
the doc comment asserts is enforced and is not. The sibling static one declaration up,
`TRACING_LOG_TARGET_PATH` (`:40`), already uses exactly the right shape
(`Mutex<Option<PathBuf>>` + `let Some(..) else { return false }` at `:91-95`) — this is a
one-static-over inconsistency, not a novel design.

**WR-24 (premise unverified — do NOT assume the review is right).** The review claims the
`unwrap_or_else(|_| granted.clone())` fallback at `:111` is structurally always-false because
`canonical_log_path` is verbatim (`\\?\C:\...`, `Prefix(VerbatimDisk)`) while `granted` is
`Prefix(Disk)`, and `Path::starts_with` is component-wise. **That premise is doubtful.** This
planning session read `crates/nono/src/capability.rs`: `FsCapability::resolved` is produced by
`path.canonicalize()` at `:110`, `:144`, `:361`, and `:457` — so the production values fed to
`set_granted_read_paths` (`launch.rs:1648`, `c.resolved.clone()`) are ALREADY verbatim, and the
fallback would compare verbatim-against-verbatim and match correctly. The review's prescribed
fix (`return true` on canonicalisation failure) would then be a *behaviour change with no bug
behind it*: it would flip a legitimately-granted-but-not-yet-existing target to "covering",
suppressing layer detail on a channel that is genuinely private. There are two known routes to a
NON-canonical `granted` — `capability.rs:1455` (`cap.resolved = rewritten`) and the
`set_granted_read_paths_for_test` seam — so a real defect may exist on a narrower path than the
review describes. **This plan proves which, by execution, before it changes anything.**

Purpose: make every fail-secure case `log_target_is_private()` documents both representable and
implemented, and settle WR-24's disputed premise with a test rather than a prescription.
Output: an `Option`-typed `GRANTED_READ_PATHS` with a matching not-yet-populated test; an
empirical verdict on the fallback branch with a fix matched to it; and a claim-to-test
enumeration proving no fourth documented case is unimplemented.
