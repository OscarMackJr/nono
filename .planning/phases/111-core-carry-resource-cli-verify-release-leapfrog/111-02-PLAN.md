<objective>
Correct the stale, false CLI help text for `--memory`, `--timeout`, and `--max-processes` in
`crates/nono-cli/src/cli.rs` (and its identical-defect twin in `docs/cli/usage/flags.mdx`), which
currently claims these three flags are "accepted with a warning pending cross-platform follow-up"
on Linux/macOS. This is false: all three are already kernel-enforced on both platforms (cgroup v2
on Linux; `setrlimit(RLIMIT_AS/RLIMIT_NPROC)` on macOS, with a best-effort caveat for memory).

Purpose: CORE-02 is a documentation-accuracy fix, not new enforcement — correcting stale help
text that could lead a user to believe their resource limits are unenforced when they are not (or,
on macOS memory, to over-trust a best-effort guarantee as absolute).
Output: Three corrected doc comments in `cli.rs`, a corrected docs-site section in `flags.mdx`,
zero test changes (none exist to change), both mandatory cross-target clippy gates re-confirmed
GREEN on `cli.rs`.

From `crates/nono-cli/src/launch_runtime.rs` lines 187-203 (`ResourceLimits` doc comment, verbatim,
accurate today):
- Windows: kernel-enforced via Job Object (CPU, memory, process-count via
  `SetInformationJobObject`; timeout via supervisor-side `TerminateJobObject`).
- Linux: kernel-enforced via cgroup v2 delegated hierarchy; requires cgroup v2 + systemd
  delegation; fails fast on cgroup v1 hosts with `NonoError::UnsupportedKernelFeature { feature:
  "cgroup_v2", hint }` (hint points at the `cgroup_no_v1=all` boot flag).
- macOS: kernel-enforced for memory + max_processes via `setrlimit(RLIMIT_AS, RLIMIT_NPROC)` in a
  `pre_exec` hook. `--cpu-percent` is rejected at clap parse time. `--timeout` enforced via
  supervisor-side `Instant` deadline + `kill(pgrp, SIGKILL)` watchdog.

From `crates/nono-cli/src/exec_strategy.rs` lines 1134-1153 (the macOS `pre_exec` closure, verbatim
stderr message): `"nono: setrlimit(RLIMIT_AS) not enforced on macOS (best-effort); continuing\n"` —
written via async-signal-safe `libc::write` when `setrlimit(RLIMIT_AS, ...)` itself returns an
error (e.g. `EINVAL` on Apple Silicon, where dyld pre-maps hundreds of MiB of VAS before `main()`).

From `crates/nono-cli/src/exec_strategy/supervisor_macos.rs` module doc (verbatim): `RLIMIT_AS`
bounds virtual address space, not RSS — "a process can pass `--memory 256m` and still consume more
than 256 MB of physical memory if its mappings are sparse or shared." `--max-processes` on macOS
uses `RLIMIT_NPROC = baseline_uid_count + N`, which is **UID-wide**, not descendant-tree-scoped
like Linux `pids.max` — other processes owned by the same UID share the budget. This path IS
fail-closed on `setrlimit` failure (unlike the memory path, which is best-effort).

From `crates/nono-cli/src/exec_strategy/supervisor_linux.rs`'s `CgroupSession::detect()` (lines
2217-2263): requires pure cgroup v2 with systemd delegation (reads `/proc/self/cgroup`, requires
exactly one `0::` line); any v1/hybrid host fails the WHOLE launch closed with
`NonoError::UnsupportedKernelFeature` before any child spawns — not a silent skip.
